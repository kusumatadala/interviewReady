## 2. Spring Boot/JPA: race-safe transfer endpoint — 40 min

**Scenario:** Two independent requests attempt to debit a synthetic wallet with balance 100 by 80 each. Correct behavior: **at most one debit succeeds**; final balance is 20, never -60. A repeated request with the same idempotency key must return the prior result, not debit again.

**10 min — Design**
- [ ] Define `wallet(id, balance, version)`, `transfer(id, idempotency_key UNIQUE, status, amount)` with `BigDecimal` and suitable numeric precision.
- [ ] Explain `@Transactional` boundary and why reading a balance and then writing it is unsafe without coordination.
- [ ] Choose **one** consistency mechanism: `@Version` optimistic locking + retry/recheck, or a database row lock (`SELECT ... FOR UPDATE`). Explain why `synchronized` alone does not protect multiple service instances.

**20 min — Implement/test**
- [ ] Write an integration test that launches two concurrent debits using a latch/barrier and separate transactions.
- [ ] Assert exactly one successful debit, balance 20, and no negative balance. Repeat test at least 10 times to catch nondeterministic failures.
- [ ] Send the **same idempotency key** twice; assert a single persisted transfer and no second debit. Handle unique-key conflicts correctly, including concurrent duplicates.
- [ ] Add a validation test for zero/negative amount and insufficient funds.
- [ ] If PostgreSQL isn't available, implement the concurrency test against a real test database later; mark the database test **blocked**, not completed.

**10 min — Explain**
- [ ] Compare optimistic and pessimistic locking: contention, retries, deadlocks, throughput.
- [ ] Explain why `@Transactional` alone does not guarantee business-level exactly-once semantics and why Spring proxy self-invocation matters.

**Definition of done:** Race and duplicate-key tests passing against a real DB; one paragraph on chosen isolation/locking. **Artifacts:** test class, schema, test log, short design note.

**References:** [Spring transaction management](https://docs.spring.io/spring-framework/reference/data-access/transaction.html) · [Spring Data JPA locking](https://docs.spring.io/spring-data/jpa/reference/jpa/locking.html) · [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html)

## 3. Kafka: at-least-once delivery + outbox — 35 min

**Toy scenario:** A transfer succeeds in PostgreSQL; a Kafka event should trigger a notification. The service crashes between DB commit and Kafka publish.

**10 min — Model**
- [ ] Draw `HTTP → transaction(wallet + transfer + outbox) → commit → outbox publisher → Kafka → consumer → notification`.
- [ ] Define outbox columns `event_id`, `aggregate_id`, `payload`, `created_at`, `published_at`. Use a unique event ID and partition Kafka by wallet/aggregate ID when per-key ordering is required.

**15 min — Failure matrix**
- [ ] Work through five failures: (1) DB rollback, (2) crash after DB commit/before publish, (3) Kafka publish succeeds but publisher crashes before marking published, (4) consumer crashes after DB side effect/before offset commit, (5) poison message.
- [ ] For each write **what may repeat**, **what must be atomic**, and **how recovery works**.
- [ ] Explain why outbox publishing may duplicate events, and how the consumer's `processed_event(event_id UNIQUE)` inbox/idempotency table prevents duplicate business effects.
- [ ] Decide retry/backoff, DLQ, manual replay, lag alerts, and how to avoid losing failed messages.

**10 min — Explain**
- [ ] Present the design aloud in two minutes and explicitly distinguish Kafka's delivery guarantees from external DB side effects.
- [ ] Write 6–10 lines of outbox publisher pseudocode and one test idea for redelivery.

**Definition of done:** Diagram + five-row failure matrix + pseudocode + 2-minute explanation. **Artifacts:** `kafka-outbox-design.md`, diagram (Mermaid allowed).

**References:** [Kafka design and delivery semantics](https://kafka.apache.org/documentation/) · [Confluent delivery semantics](https://docs.confluent.io/kafka/design/delivery-semantics.html)
