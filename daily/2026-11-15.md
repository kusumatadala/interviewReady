## 2. Spring Boot/JPA: concurrency and transaction isolation — 40 minutes

**Scenario:** Two API calls attempt to debit 80 units from the same synthetic wallet balance of 100. Exactly one debit should succeed; the other must fail safely. Avoid presenting a race as fixed merely because sequential tests pass.

**Concepts — 10 min**
- [ ] Explain read-committed vs repeatable-read vs serializable in terms of concurrent writes, not just definitions.
- [ ] Contrast JPA `@Version` optimistic locking, `LockModeType.PESSIMISTIC_WRITE`, and atomic conditional SQL `UPDATE wallet SET balance = balance - :amount WHERE id=:id AND balance >= :amount`.
- [ ] Explain how `@Transactional` and exception rollback interact with locking; a transaction boundary alone does not eliminate lost updates.

**Implementation — 25 min**
- [ ] Create `Wallet(id, balance, version)` and `POST /wallets/{id}/debits` with synthetic inputs.
- [ ] First reproduce a race using two parallel requests and a latch/barrier in a test (avoid fragile sleep-only timing).
- [ ] Fix it with **one** explicit strategy: optimistic version check + bounded retry, pessimistic DB lock, or atomic conditional update.
- [ ] Write integration tests for (1) sufficient funds, (2) insufficient funds with no mutation, (3) simultaneous debits from balance 100 with both requests asking for 80. Assert final balance is 20, never negative; exactly one business debit succeeds.
- [ ] If using H2, note that PostgreSQL's real locking/isolation behavior must be validated against PostgreSQL (e.g. Testcontainers) before claiming production equivalence.
- [ ] Record the SQL and explain how two service replicas are coordinated by the database, not a JVM-local lock.

**Explain — 5 min**
- [ ] Answer aloud: What would change if the wallet update and an external payment API call were inside the same transaction?

**Definition of done:** A documented failing concurrency test before the fix (or a reproducible interleaving), a passing test afterward, and a 90-second isolation/locking explanation.  
**Expected artifacts:** `WalletServiceTest.java`, endpoint contract, test output, one locking trade-off note.  
**References:** [Spring transaction management](https://docs.spring.io/spring-framework/reference/data-access/transaction.html) · [Spring Data JPA locking](https://docs.spring.io/spring-data/jpa/reference/jpa/locking.html) · [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html).

## 3. Kafka: recovery, deduplication and poison messages — 35 minutes

**Scenario:** A Kafka consumer receives `WalletDebited(eventId,walletId,amount)`. A process can crash after database commit but before Kafka offset acknowledgement; another event has invalid schema.

**Design — 15 min**
- [ ] Sketch `producer → wallet-events topic (key=walletId) → consumer → database inbox + projection → outbox → notification worker`.
- [ ] Define `processed_events(event_id PRIMARY KEY, processed_at)` and update it in the **same DB transaction** as the projection. Duplicate `eventId` should not reapply the debit.
- [ ] Explain the crash windows: before DB commit; after DB commit/before offset commit; after offset commit.
- [ ] Decide retry policy: bounded exponential backoff for transient DB failures; quarantine/DLQ for unrecoverable schema/validation failures, with original topic/partition/offset and error metadata.
- [ ] Explain why Kafka exactly-once semantics alone do not guarantee exactly-once effects in an external database, and why an outbox publisher itself may deliver twice.

**Practice — 15 min**
- [ ] Write pseudocode or a small JUnit test for duplicate delivery of the same event ID: projection changes once, processed-events row appears once.
- [ ] Draw a **5-row failure matrix**: DB temporarily unavailable; duplicate event; consumer crash after DB commit; poison message; outbox published but marker update fails. For each, record observed symptom, recovery, and invariant.
- [ ] Name 4 operational metrics: consumer lag, retry count, DLQ volume, and outbox oldest-unpublished age.

**Explain — 5 min**
- [ ] Give a two-minute whiteboard explanation of the difference between message delivery guarantees and business-effect guarantees.

**Definition of done:** Diagram, five-row failure matrix, one tested or explicitly pseudocoded deduplication rule, and clear failure/recovery explanation.  
**Artifacts:** `docs/kafka-recovery.md`, diagram, optional test.  
**References:** [Kafka documentation](https://kafka.apache.org/documentation/) · [Spring Kafka reference](https://docs.spring.io/spring-kafka/reference/) · [PostgreSQL unique constraints](https://www.postgresql.org/docs/current/ddl-constraints.html).
