### 2. Spring transactions, locking, JPA — 40 min

**Read and reason (10 min)**
- [ ] Explain `@Transactional` proxy boundaries, default rollback for unchecked exceptions, and the difference between DB transaction atomicity and thread safety.
- [ ] Compare optimistic locking (`@Version`) vs pessimistic row locking and explain why a read-then-write balance check can race.
- [ ] Explain why `synchronized` on one application instance does **not** protect across multiple service instances.

**Implement and test (25 min)**
- [ ] Model `Account(id, balance, version)` with `@Version`. Implement `transfer(fromId, toId, amount, transferId)` in one service transaction.
- [ ] Validate amount > 0, sufficient funds, and a unique `transferId` (idempotency); use a unique DB constraint. Avoid double-entry claims unless both debit and credit entries are recorded.
- [ ] Create a test with **two concurrent transfers from the same account**. Coordinate start with `CountDownLatch`; capture one successful update and one optimistic-lock failure/retry path, or explain DB-specific behavior if not reproducible.
- [ ] Assert no negative balance and conservation of total funds after successful operations. Record transaction boundaries and the SQL/exception seen.
- [ ] State how bounded retry with backoff should work for an optimistic conflict and why retrying a non-idempotent external call inside a transaction is dangerous.

**Explain (5 min)**
- [ ] Give a 90-second answer: *How would you prevent double spending with multiple pods and concurrent requests?*

**Definition of done:** One runnable test demonstrating concurrency behavior (or a precise blocker), clear invariant assertions, and a defensible choice of locking strategy.

**References:** [Spring transaction reference](https://docs.spring.io/spring-framework/reference/data-access/transaction.html), [Spring Data JPA locking](https://docs.spring.io/spring-data/jpa/reference/jpa/locking.html), [Java concurrency](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/package-summary.html).

### 3. Kafka + outbox + failure recovery — 40 min

**Scenario:** After a successful transfer, publish `TransferCompleted` for notifications and reporting without sending duplicate notifications if events are replayed.

**Design (15 min)**
- [ ] Draw the sequence `POST /transfers → transaction (account changes + transfer ID + outbox row) → commit → outbox publisher → Kafka → notification consumer → inbox/dedup table → notification`.
- [ ] Explain why **database update + direct Kafka send** is a dual-write problem. State the transactional outbox's benefit and its limitation (publisher can emit duplicates).
- [ ] Define topic key `accountId` or `transferId`, compare ordering trade-offs, and specify event schema with `eventId`, `transferId`, `occurredAt`, and `schemaVersion`.

**Failure matrix (15 min)**
- [ ] A: Crash before DB commit — expected account/outbox state.
- [ ] B: DB commits, service crashes before response — retry with same `transferId`.
- [ ] C: Outbox publisher sends to Kafka, crashes before marking sent — duplicate publish.
- [ ] D: Consumer commits DB dedup record, crashes before offset commit — redelivery.
- [ ] E: Poison event / temporary dependency outage — retry budget, backoff, DLQ, alert.
- [ ] Specify unique indexes and atomic DB transactions that keep *business effects* idempotent; distinguish Kafka's exactly-once facilities from arbitrary external side effects.

**Interview drill (10 min)**
- [ ] Explain 2-min end-to-end design and 1-min monitoring plan: lag, retries, DLQ, outbox backlog, duplicate count, end-to-end latency.
- [ ] State a safe replay process and how to prevent sending duplicate external notifications (idempotency key at provider or explicit delivery state, with limitations).

**Definition of done:** One diagram, a 5-case failure table with recovery, and a 2-minute explanation.

**References:** [Kafka documentation](https://kafka.apache.org/documentation/), [Confluent delivery semantics](https://docs.confluent.io/kafka/design/delivery-semantics.html), [Transactional outbox pattern](https://microservices.io/patterns/data/transactional-outbox.html).
