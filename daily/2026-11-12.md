## 2. Kafka reliability and system design — 35 minutes

**Toy scenario:** A consumer receives case-state events, updates a database record, and may be restarted between database commit and Kafka offset commit. One business action must not be applied twice.

### Design (20 minutes)
- [ ] Draw `producer → topic → consumer group → DB + outbox → notification sender`.
- [ ] Choose a stable idempotency key, e.g. `(sourceSystem, eventId)`, protected by a database unique constraint.
- [ ] Explain the atomic DB transaction: insert inbox/idempotency marker → mutate business state → insert outbox event → commit.
- [ ] Commit or acknowledge the Kafka offset **after** successful DB commit.
- [ ] Walk through a crash after DB commit but before offset commit; explain expected redelivery and why the unique key prevents a duplicate business effect.
- [ ] Describe transient-retry backoff, poison events/dead-letter topics, replay, and observability.
- [ ] Discuss partitioning by `caseId`, per-key ordering, consumer lag, partition count, and throughput.
- [ ] Note that Kafka's own producer idempotence/transactions do not automatically ensure exactly-once side effects in an external database.

### Explain (15 minutes)
- [ ] Create a 3-row failure table: before DB commit; after DB commit/before offset; after offset commit.
- [ ] Explain how you would validate consistency under retries, process crashes, and duplicate messages.
- [ ] Give a 2-minute spoken architecture walkthrough using clear, non-confidential examples.

**Definition of done:** One diagram, three failure cases with recovery behavior, and a two-minute design explanation.  
**References:** [Apache Kafka docs](https://kafka.apache.org/documentation/) · [Confluent delivery semantics](https://docs.confluent.io/kafka/design/delivery-semantics.html)

- [ ] Explain effect on transaction boundaries/rollback behavior.
- [ ] Suggest a solution: extract separate Spring bean or use `TransactionTemplate`.

### Q2. Kafka consumer commits a DB write, crashes, then restarts before committing its Kafka offset. What happens?
- [ ] Recognize at-least-once redelivery.
- [ ] Separate delivery from exactly-once **business effects**.
- [ ] Explain unique idempotency key, inbox, or deduplication record.
- [ ] Cover database transaction + outbox and commit ordering.
- [ ] Cover retry, DLQ, observability, and replay safety.

**Self-test pass mark:** At least 4 of 5 items for each answer, in your own words.
