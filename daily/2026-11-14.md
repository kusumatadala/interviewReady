## 2. Spring Boot REST, JPA, and idempotency — 40 min

**Concepts (10 min)**
- [ ] Explain `@Transactional` boundaries, rollback on unchecked exceptions, and why a repository call is not automatically a completed transaction.
- [ ] Explain the difference between a duplicate HTTP request and a duplicate *business operation*.
- [ ] Contrast `@Version` optimistic locking and a database unique constraint; when does each solve a different problem?

**Hands-on (25 min)**
- [ ] Design `POST /transfers` with `Idempotency-Key` header and JSON `{fromAccount,toAccount,amount}` using only synthetic account IDs.
- [ ] Store a unique `idempotency_key` with the operation result; reject the same key with a different request payload (e.g., HTTP 409), and return the stored response for an exact replay.
- [ ] In one DB transaction: validate nonnegative amount and available balance; debit, credit, persist transfer result and idempotency record.
- [ ] Add tests: first call succeeds; same key and payload returns same transfer ID without a second debit; same key/different payload conflicts; insufficient funds rolls back; two concurrent requests with the same key result in **one** business effect.
- [ ] Write a note on how to handle concurrent unique-key races: catch the conflict, read committed result, or return a retryable response; don't silently return an incomplete record.

**Explain (5 min)**
- [ ] Give a 60-second explanation of why in-memory `synchronized` alone is insufficient across multiple replicas.

**Done when:** At least three tests pass and the remaining tests are documented with actual failures; explain the cross-instance race. Do not mark complete merely for writing pseudocode.  
**Evidence:** `TransferServiceTest` output, endpoint contract, short note on isolation and uniqueness.  
**References:** [Spring transactions](https://docs.spring.io/spring-framework/reference/data-access/transaction.html), [Spring Data JPA locking](https://docs.spring.io/spring-data/jpa/reference/jpa/locking.html), [PostgreSQL unique constraints](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS)

## 3. Kafka reliability + outbox design — 35 min

**Scenario:** Publish a `TransferRecorded` event after a successful database transfer. The service can crash at any time.

- [ ] Draw `HTTP request → DB transaction (balances + idempotency + outbox) → outbox publisher → Kafka → notification consumer`.
- [ ] Explain why `DB commit; kafka.send()` is a dual-write hazard and why an outbox row in the same DB transaction reduces it.
- [ ] Design `outbox(id, aggregate_id, event_type, payload, created_at, published_at)` with only synthetic payload fields.
- [ ] Draw a **five-row failure matrix**: crash before DB commit; crash after DB commit/before publish; publish succeeds/ack lost; duplicate Kafka delivery; consumer fails repeatedly.
- [ ] Describe producer retries, at-least-once delivery, a unique consumer inbox key, retry backoff and DLQ policy; identify when to alert and replay.
- [ ] Explain ordering per `aggregate_id` via Kafka key and partition, and why global ordering is not guaranteed.
- [ ] Write three monitoring signals: outbox backlog age, consumer lag, DLQ count; state one actionable threshold strategy (e.g., baseline-dependent, not invented production SLA).
- [ ] Rehearse a two-minute system design walkthrough and name one limitation of the approach.

**Done when:** Diagram + five failure cases + duplicate-effect mitigation + monitoring explanation are written and spoken.  
**Evidence:** `outbox-design.md` or Mermaid diagram and failure matrix.  
**References:** [Kafka documentation](https://kafka.apache.org/documentation/), [Confluent delivery semantics](https://docs.confluent.io/kafka/design/delivery-semantics.html), [Debezium outbox event router](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html)

**Q1 — Two identical POST requests hit different service replicas simultaneously. How do you prevent duplicate transfers?**
- [ ] Identify cross-instance concurrency and retry behavior.
- [ ] Require a stable client idempotency key and unique DB constraint.
- [ ] Keep balance mutations and result/idempotency record in one transaction.
- [ ] Explain race handling, same-key/different-payload conflict, and retry semantics.
- [ ] Mention optimistic locking/transaction isolation as appropriate, without claiming either replaces idempotency.

**Q2 — Outbox event was published to Kafka but the publisher crashed before marking it published. What happens?**
- [ ] Explain likely republish and at-least-once delivery.
- [ ] Use a stable event ID for downstream deduplication.
- [ ] Keep consumer inbox and business effect in the same DB transaction.
- [ ] Explain monitoring, retry, and DLQ/replay policy.
- [ ] State why Kafka transactions alone don't guarantee external DB side effects.
