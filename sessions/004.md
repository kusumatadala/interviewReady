# Session 004 — SQL — indexes and EXPLAIN

**40 minutes · Core foundations · No assigned calendar date**

**Goal:** Use actual query plans to reason about a real relational database performance trade-off.  
**Prerequisite:** Session 003 or a documented equivalent skill.  
**Sources:** [PostgreSQL EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html) · [Indexes](https://www.postgresql.org/docs/current/indexes.html)

## 1. Recall / learn — 5 minutes
- [ ] Define selectivity and why indexes are not always chosen.
- [ ] Compare index scans with sequential scans in a small table.

## 2. Hands-on practice — 25 minutes
- [ ] Generate 10,000 synthetic `orders(id, customer_id, status, created_at)` rows (no real customer data).
- [ ] Run `EXPLAIN (ANALYZE, BUFFERS)` on a query filtering by `customer_id` and ordered by `created_at DESC`; record actual plan and timings.
- [ ] Create index `(customer_id, created_at DESC)`, re-run exactly the same query and compare.
- [ ] Test a low-selectivity query (e.g., majority `status`) and observe when the planner prefers a scan; keep or remove indexes based on evidence.

## 3. Verify / explain — 10 minutes
- [ ] Write a before/after table including scan node, rows, timing and index DDL.
- [ ] Explain index maintenance cost, write overhead and why a composite index column order matters.

**Definition of done:** Two EXPLAIN outputs compared and one evidence-based explanation; if PostgreSQL unavailable, mark blocked and prepare the queries.

**Expected evidence:** `schema.sql`, `indexes.sql`, `explain-results.md` using synthetic data

### Mock interview check
**Question:** Why might adding an index fail to speed up a query?

**Answer should cover:**
- [ ] Planner selectivity
- [ ] Table size and cache
- [ ] Index prefix/column order
- [ ] Write overhead
- [ ] Measure with EXPLAIN ANALYZE
